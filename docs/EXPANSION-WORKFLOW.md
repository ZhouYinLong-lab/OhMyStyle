# 风格包扩充工作流

本文件定义 OhMyStyle 后续扩充的标准流程。默认以 **20 个风格包为一个完整批次**，每个包都必须有独立研究、代表图、双语 README 和可验证的 Prompt 规则。

## 1. 扩充批次的基本规则

- 一个正式扩充批次必须规划并登记 **恰好 20 个包**；不能用 3 个文件改动伪装成 20 个包，也不能用重复模板填充数量。
- 20 个包可以来自一个或多个大分类，但每个包都必须明确自己的 `category`、`kind`、研究对象和风格边界。
- 每一个包都是独立交付单元：先完成并验证一个包，再提交该包的 commit；批次级目录索引、画廊和统计信息在包完成后统一更新。
- 若确实不能按 20 个包完成，必须在批次记录中写明原因、已完成数量和后续拆分计划；默认不把不完整批次标记为完成。
- 交叉风格不是独立风格包数量，不计入 20 个包；它只引用已经存在的基础包。

批次记录使用 [`templates/expansion-batch.yaml`](../templates/expansion-batch.yaml)。实际批次记录建议放在 `batches/YYYY-MM-batch-XX.yaml`，并用校验器检查。

## 2. 每个包的完成顺序

### 2.1 先研究原作品，再提取风格

艺术家、摄影师、流派、学校、工艺和游戏美术包，都必须先取得可追溯的原作品或一手视觉资料，再提取可观察的风格规则。只收集文字介绍，不足以完成一个成熟风格包。

研究至少应回答：

1. 参考作品来自哪里，作品或页面的标题、作者、机构和 URL 是什么；
2. 参考图的权利状态是什么，能否放入仓库，不能再分发时如何只保留链接和描述；
3. 哪些特征在不同主题中仍然稳定，例如媒介、边缘、构图、光线、色彩、材质、空间或颗粒；
4. 哪些特征只是某一件作品的内容，不应写进基础 Prompt；
5. 生成样例如何标注为新生成内容，避免被误认为原作或官方作品。

研究结果写入 `references/manifest.csv` 和 `provenance.yaml`。参考原作与仓库中的新生成样例必须分开存放并清楚标注。

### 2.2 建立主体无关的风格契约

风格包描述“如何呈现”，不规定“每次画什么”。基础 Prompt 必须：

- 使用 `{SUBJECT}` 和 `{LOCATION}` 占位符；
- 保留主体独立契约，并设置 `identity.yaml` 的 `scope.subject_policy: open`；
- 只写媒介、构图、光线、色彩、材质、纹理、空间和边缘行为；
- 不把桥梁、房屋、人物、城市、花卉、车辆、地标或固定叙事写成默认主体；
- 把具体场景放到 `examples/` 或 benchmark，并明确它只是测试输入。

如果某个包的名称来自一部游戏、一个系列或一位作者，也只能提取其稳定的视觉规则，不能让包在每次运行时自动生成该作品中的固定地点、角色或道具。

### 2.3 原生生成代表图和样例

- 每个包至少需要一张原生横版 16:9 `gallery-16x9.jpg`；不得先生成竖图再裁切、拉伸或拼接成画廊图。
- 代表图必须体现风格特征，而不是只体现一个具体对象；可使用中性、可替换的主题。
- 新生成图片放入 `examples/generated/`，通过人工审核后才进入 `examples/accepted/`；元数据必须记录模型、提示词、日期和生成状态。
- 参考原作、游戏截图、摄影作品和艺术家作品不能被伪装成生成样例，也不能在权利不清楚时直接打包。

### 2.4 完成用户文档

每个包必须同时提供 `README.md` 和 `README.en.md`，并面向使用者说明：

- 这个包稳定控制什么视觉特征；
- 它不默认控制什么主体；
- 参考来源与权利边界；
- 生成 Prompt、负面约束和变量的使用方法；
- Agent、云端 API 或本地模型的执行方式；
- 代表图和生成样例的身份标注。

## 3. 单包验收门槛

| 门槛 | 必须满足 |
| --- | --- |
| 研究 | 有原作品或一手视觉资料，有可追溯来源 |
| 权利 | `provenance.yaml` 和 `references/manifest.csv` 完整，未把无权再分发素材打包 |
| 结构 | 模板要求的文件齐全，版本和注册表信息一致 |
| 风格 | 基础 Prompt 只描述视觉规则，主体策略为 `open` |
| 生图 | 有原生 16:9 代表图和至少一个已标注的生成样例 |
| 文档 | 中英文 README 面向使用者，中文不是逐句机翻英文 |
| 校验 | 包、资源、benchmark、主体独立性和测试全部通过 |

## 4. 提交与批次状态

推荐的单包 commit 格式：

```text
feat: add style package <category>/<id>
```

一个包一个 commit。批次索引、总 README 画廊和统计信息可以在 20 个包完成后使用独立的批次 commit；该 commit 不能替代任何一个包的独立 commit。

批次状态建议按以下顺序推进：

```text
planning -> research -> building -> review -> complete
```

只有 20 个包都满足单包验收门槛、批次校验通过、总 README 已更新且 `git diff --check` 通过时，批次才能标记为 `complete`。

## 5. 批次校验

创建或更新批次记录后运行：

```powershell
python tools/validate-expansion-batch.py batches/2026-08-batch-01.yaml
```

校验器至少检查：

- `target_count` 是否为 20；
- 是否正好列出 20 个不同的包 ID；
- 分类计划的数量是否合计 20，并与包清单一致；
- 完成批次中的每个包目录、`package.yaml`、代表图和双语 README 是否存在；
- 每个完成包是否记录了来源、校验状态和独立 commit。

批次记录只描述工作状态，不复制风格包内容。真正的风格规则仍以每个包目录中的结构化文件为准。
